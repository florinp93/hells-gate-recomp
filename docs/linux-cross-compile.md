# Building and running on Linux (native cross-compile + Proton)

This documents a full path from a fresh Fedora/Linux checkout to a playable
build under Proton, without ever touching Windows or Visual Studio. Everything
here was exercised end-to-end (build, codegen against the real XEX, and
several hours of actual play) on Fedora 44 (KDE Plasma, Wayland), an AMD
Strix Halo (Radeon 8060S) integrated GPU, GE-Proton11-6.

## 1. Cross-compiling the Windows (D3D12) target from Linux

No Windows, no Wine, no VM needed for the build itself - only to *run* the
resulting `.exe` afterwards.

**Toolchain:** `clang-cl` (LLVM's MSVC-compatible driver - ships with recent
Fedora `clang` packages) targeting `x86_64-pc-windows-msvc`, against a
Windows SDK + MSVC CRT snapshot fetched by
[`xwin`](https://github.com/Jake-Shadle/xwin) (`cargo install xwin --locked`).
See `cmake/toolchains/windows-clang-cl-xwin.cmake` in this repo - it's
self-contained and documents each workaround inline (case-sensitivity
mismatches between Linux and the Windows SDK's own headers, missing debug CRT
libs, `mt.exe` unavailability, MSVC vs. GNU flag spellings, etc.).

```bash
cargo install xwin --locked
XWIN_ACCEPT_LICENSE=1 xwin --accept-license --cache-dir ~/.local/opt/xwin-cache \
    splat --include-debug-libs --output ~/.local/opt/xwin-sdk

cmake -S . -B out/build/win-cross -G Ninja \
    -DCMAKE_TOOLCHAIN_FILE=cmake/toolchains/windows-clang-cl-xwin.cmake \
    -DXWIN_SDK_PATH=$HOME/.local/opt/xwin-sdk \
    -DREXSDK_DIR=thirdparty/rexglue-sdk \
    -DCMAKE_BUILD_TYPE=Release
cmake --build out/build/win-cross
```

The whole SDK (SDL3, Tracy, spdlog, SPIRV-Tools, VMA, rexglue core, ~700+
files) compiles cleanly this way, producing real PE32+ binaries
(`dantes_inferno.exe`, `rexruntime.dll`, `rexgpu-xenos.dll`, `TracyClient.dll`).

### The rexglue.exe-under-Wine gotcha

The build's codegen step runs `rexglue.exe` (cross-compiled, so it only runs
under Wine) as a Ninja custom command. `generated/rexglue.cmake` (SDK-managed,
regenerated by every `rexglue codegen` run) passes the manifest path as an
**absolute POSIX path**. Under Wine, CLI11 (compiled for the Windows target)
treats a leading `/` as a Windows-style option prefix (like `/help`) and
rejects the whole argument with "argument not expected" - it works fine on
real Windows only because a Windows absolute path never starts with `/`.

Fix: edit the `COMMAND` line in `generated/rexglue.cmake` to pass a **relative**
path (`dantes_inferno_manifest.toml`, matching its `WORKING_DIRECTORY`, already
set to `CMAKE_CURRENT_SOURCE_DIR`) instead of `${CMAKE_CURRENT_SOURCE_DIR}/...`.
This reverts every time codegen regenerates the file (it's the SDK's own
`AlwaysRegenerate` boilerplate) - reapply it whenever a build regresses to the
absolute-path failure, right before the next `cmake -S . -B ...` reconfigure.

### Building `rexglue` itself natively (faster iteration)

`rexglue` is a pure host build tool - it doesn't need to be a Windows binary
at all. Configuring it as a plain native Linux target (no cross toolchain)
gives a real ELF that runs directly, with normal native compile speed and
none of the Wine-argv quirks above - much nicer for iterating on the SDK's
codegen itself:

```bash
cmake -S thirdparty/rexglue-sdk -B out/build/rexglue-host -G Ninja \
    -DCMAKE_BUILD_TYPE=Release \
    -DCMAKE_C_COMPILER=clang -DCMAKE_CXX_COMPILER=clang++ \
    -DCMAKE_C_FLAGS="-march=x86-64-v2" -DCMAKE_CXX_FLAGS="-march=x86-64-v2"
cmake --build out/build/rexglue-host -j$(nproc) --target rexglue
```

## 2. Discovering unresolved functions by actually playing

`codegen`'s static discovery (call-graph expansion + `VTableScanner`'s
MSVC-RTTI vtable scan, ~371 vtables / 576 functions found on this XEX) misses
a handful of functions reached through mechanisms it doesn't cover - not
vtables, not `lis`/`addi`-computed pointers in code (checked: temporarily
enabling `functionPointerScan()` in `thirdparty/rexglue-sdk/src/codegen/
phase_discover.cpp`, disabled upstream for "too many false positives", found
1969 candidates and **none** matched our real misses - most likely these are
plain function-pointer tables stored as data, a pattern none of the SDK's
three discovery passes currently cover).

These only surface as `[FATAL] Call to invalid or unregistered function at
guest address 0x...` crashes at runtime, at the exact point the game first
calls them. The manifest's `unresolved_target_*` entries already document
~50+ such addresses found this way over the project's history; the 8 below
were found in this same manner while cross-compiling on Linux and playing
through the prologue and the first boss fight:

```
0x82452448  0x826BA5E0  0x826BEDF8  0x826BF6B0
0x8231C848  0x8231C828  0x82325360  0x822C0CA8
```

Workflow when you hit a new one: add `[entrypoint.functions.0x<ADDR>]` /
`name = "unresolved_target_<ADDR>"` to `dantes_inferno_manifest.toml`
(matching the existing entries' style), reapply the `generated/rexglue.cmake`
relative-path patch (see above), reconfigure, rebuild, relaunch.

## 3. Rendering: what actually needs to change on Linux vs. what doesn't

**`game_data_root` must be a CLI flag, not `dantes_inferno.toml`.**
`ReXApp::SetupEnvironment()` (`thirdparty/rexglue-sdk/src/ui/rex_app.cpp`)
builds `PathConfig` - and locks in `game_data_root_` from whatever the
`game_data_root` cvar already holds - **before** it calls `LoadConfig()` on
the TOML file (deliberately: log cvars need to be live for the rest of
startup). A `game_data_root` set only in the config file is silently too
late and the game refuses to start ("--game_data_root was not provided").
Verified directly: setting it only in the TOML reproduces the error every
time; passing it as `--game_data_root=...` works. (This is a correction to
this repo's own `a8a3282` "Fix install paths with apostrophes" commit, whose
premise - "the game already reads game_data_root from the TOML" - doesn't
hold up against the actual `SetupEnvironment()` code path. The apostrophe-
mangling bug that commit was chasing is real, but the right fix is to escape
`ProcessStartInfo.Arguments` correctly, not to drop the CLI arg - the launcher
targets .NET Framework 4.0, so `ArgumentList` isn't available; correct Win32
command-line quoting has to be built by hand.)

**`--render_target_path_d3d12=rov` makes gameplay *worse* here, not better.**
The existing guidance (`src/dantes_inferno_app.h`'s comment, and the C#
launcher's hardcoded `args.Add("--render_target_path_d3d12=rov")`) is to
always force ROV because the default host-RT (RTV/DSV) path corrupts
pre-rendered VP6 FMV video. That FMV corruption is real, but it isn't a
render-target-path issue at all - it's the VMX/AltiVec vector-instruction
recompiler bug already fully diagnosed in `docs/vp6_fmv_corruption_fix.md`
and submitted upstream as
[rexglue/rexglue-sdk#426](https://github.com/rexglue/rexglue-sdk/pull/426)
(open, not yet merged as of this writing). Once that fix is applied to a
`thirdparty/rexglue-sdk` checkout (it's SDK code, gitignored here, so it
can't live in this repo - apply the diff from `docs/vp6_fmv_corruption_fix.md`
by hand, rebuild `rexgpu-xenos.dll`), **the opening FMV and every loading
screen render perfectly cleanly with `render_target_path_d3d12` left at its
default (unset)** - verified on this box.

`rov` itself, independently, causes heavy vertical-striped noise across
*general 3D gameplay* on this GE-Proton11-6 + vkd3d-proton + Strix Halo
combination - confirmed by screenshotting the exact same combat encounter
with and without the flag. This is a separate bug from the VP6/FMV one (it
reproduces with or without the vector-instruction fix applied) and is
presumably specific to vkd3d-proton's pixel-shader-interlock emulation,
not something reproducible on native Windows/D3D12.

**Net result on Linux: leave `render_target_path_d3d12` unset (its default)
and apply the vpkuwus/vpkuhus vector fix.** That combination rendered a full
opening cutscene, every loading screen, and an entire combat encounter
(health/soul HUD, blood, fire, weapon-swing trails, "Citadel of Acre" title
card) with zero visible corruption.

## 4. Graphics/quality cvars actually available

Two things worth calling out for the Linux setup specifically:

- **GPU cvars must be CLI flags, same class of issue as `game_data_root`,
  different cause:** `resolution_scale`, `anisotropic_override`,
  `swap_post_effect`, etc. live inside `rexgpu-xenos.dll`, which isn't loaded
  until *after* `OnPreSetup()` returns - so `rex::cvar::SetFlagByName()`
  calls made from `OnPreSetup` silently fail because the cvar doesn't exist yet. CLI args work because
  `cvar::Init()` stashes unrecognized `--name=value` pairs as pending values,
  applied automatically once the owning plugin registers the cvar later - a
  TOML-file value has no equivalent pending-application mechanism for cvars
  not yet registered at `LoadConfig()` time. (`REXCVAR_SET()` may go through the same pending-value path as CLI args rather
  than `SetFlagByName()`'s immediate-only one - not verified here, but worth
  checking before relying on `OnPreSetup` to configure these.)
- **FidelityFX (CAS/FSR) is off by default** (`-DREXGLUE_ENABLE_FIDELITYFX=ON`
  at configure time to enable `present_effect=cas/fsr/fsr2/fsr3` - marked
  "experimental" in the SDK's own `CMakeLists.txt`; not tested on Linux here).

`scripts/run-linux.sh` now starts the game with the native renderer
(`--renderer=dante`, DiligentCore on Vulkan), which doesn't go through
vkd3d-proton; of the flags below it only uses `anisotropic_override`. With the emulated
renderer (`--renderer=xenos`), this recipe was used, no rebuild required
beyond the vector-instruction fix above:

```
--draw_resolution_scale_x=2 --draw_resolution_scale_y=2   # 2560x1440 internal
--anisotropic_override=5                                  # 16x aniso
--native_2x_msaa=true                                     # matches Xbox 360 HW AA
--present_dither=true                                     # hides sky/light-gradient banding
```

2x resolution scale was picked over 3x (3840x2160, native to a 4K panel) on
this specific GPU (AMD Strix Halo / Radeon 8060S) because a sibling ReXGlue
port on the same hardware (`ac6recomp`) measured a steep performance cliff at
3x; not independently re-measured for Dante's Inferno.

## 5. Deployment layout used for testing

```
dantes_inferno.exe
rexruntime.dll  TracyClient.dll  rexgpu-xenos.dll  # rexgpu-xenos also keeps sync under renderer=dante
game/                    # default.xex, bigfile0.viv, bigfile1.viv, avatarassetpack, nxeart
scripts/run-linux.sh     # see below
```

`scripts/run-linux.sh` is a generic version of the launcher script used for
testing - dedicated Proton prefix next to the game (survives reboots, unlike
`/tmp`), first-run-builds-prefix handling, and `--renderer=dante` plus
`--game_data_root` (§3). Extra arguments are passed to the game.

The Qt launcher in `launcher-linux/` is for the native Linux build: it is
built with the game when Qt 6.4+ is found (`DANTESINFERNO_BUILD_LAUNCHER`,
on by default) and packaged by `packaging/appimage/`.
